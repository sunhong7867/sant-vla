# 수집 통과율 수정(ego 전용 위치 스트림) + r44(회피 반반) 계획 (2026-10-02 10:38)

[20261002_1006](20261002_1006_r43-paired-groups-stat-eval.md)의 r43 은 회피 시연이 19 개뿐이라(직진 256) 꺾지 않았다.
사용자 지적: "회피가 너무 적어서 직진하는 것 아니냐 — 그래서 반반으로 하고 싶었던 것". 맞는 지적이고, 앞서 내가 "회피 가중치
×4 때문에 실제 비중은 반반에 가깝다"고 한 것은 **확인 없이 한 틀린 말**이었다(×4 가 붙는 프레임은 전체의 8 %, 그중 1 606 은
v0 짝; 추정 회피 표본 비중 약 20 %). 그래서 (1) 수집 통과율을 고치고 (2) 반반 데이터로 다시 학습한다.

## 1. 탈락 원인 — 위치 기록이 뭉텅이로 끊김

boxtri(360 ep) 탈락 276 의 두 사유:

| 사유 | 수 | 실제 원인 |
|---|---|---|
| 회전 중 위치 보간 오차 > 6 cm | 154 | 위치 기록 0.3~1.4 s 공백 |
| tf 스트림 공백 → "ego 재식별" | 116 | 공백 사이 차가 1.0~1.6 m 이동 → 인덱스는 그대로(0)인데 점프로 판정 |

조사:

1. tf(브리지)와 CLI 두 위치 기록의 **공백 시각이 정확히 겹쳤다**(ep_0100: 3472.33 0.43 s, 3478.3 0.32 s … 둘 다 동일). 카메라는
   30 Hz, 최대 공백 0.2 s 로 멀쩡. → 둘의 공통 원천 `/world/default/dynamic_pose/info`(장면 전체 덤프)가 문제.
2. 위치를 읽는 노드마다 이 덤프를 `gz topic -e`(ruby + gz-transport-topic) 로 따로 파싱. 그중 4 개는 9/30~10/2 실행에서 남은
   **고아 프로세스**(부모 systemd)로 계속 돌고 있었다 — ruby 래퍼만 죽이고 자식은 남는 구조.
3. 재식별 판정의 경과 시간을 노드 시계(스로틀된 /clock)로 쟀는데, 이 시계가 위치 기록과 같이 멈춰 0.4 s 공백이 ~0 s 로 보였다.

## 3. 시범 수집으로 확인 (박스 3 묶음 × v0/v1/v2 = 9 ep, performance)

| 시범 | 위치 기록 | 통과 |
|---|---|---|
| tripilot 1차 | 레코더가 시뮬보다 먼저 떠 4 s 폴백으로 덤프로 돌아감 → 중단, 폴백을 "ego 가 있는데 토픽이 없을 때만" 으로 수정 | — |
| tripilot 2차 (PosePublisher, 최근 값만 폴링) | CLI 14~17 Hz, 공백 0.4~0.8 s 그대로 | 1/9 |
| tripilot 3차 (drain + 스탬프) | **CLI 46~50 Hz, 최대 공백 0.02 s** (전: 13~17 Hz, 0.4~0.7 s) | 레코더 유효 9/9, finalize(tf 라벨) 3/9 |
| 같은 세션을 **CLI 라벨로** 재처리 | | **6/9** (남은 3 = 카메라 프레임 공백 0.56~0.66 s, 별개 문제) |

finalize 는 **tf 로 라벨을 만들고 있었다**(`--pose-source tf`). 두 스트림 비교(같은 세션):

| | ego 전용(CLI) | tf 브리지 |
|---|---|---|
| 첫 주행 명령 → 움직이기 시작 | **+0.19~0.36 s** (일정, 가속 지연으로 자연스러움) | +0.26~0.77 s (들쭉날쭉) |
| 연속 같은 타임스탬프 비율 | 0 % | 55~62 % |
| 두 스트림 위치 차(같은 시각) | 중앙 0.3~0.9 m, 최적 시간 이동 약 −0.4 s 후에도 p95 0.4~1.1 m | |

→ 새 수집은 CLI 라벨. **옛 코퍼스(tf 라벨)도 위치가 0.2~0.4 s 늦게 찍혔을 가능성** — 라벨 중 위치에서 나오는 항목이 무엇인지와
영향 크기는 미확인. 새 데이터(CLI)와 옛 데이터(tf)를 섞어 학습할 때 시간 정렬 차이가 생길 수 있다.
