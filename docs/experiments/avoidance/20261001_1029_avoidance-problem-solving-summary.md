# 장애물 회피 학습 — 문제를 어떻게 좁히고 풀었나 (2026-09-29 ~ 10-01 종합, 2026-10-01 10:29)

이틀간의 회피 실험을 문제 해결 순서로 다시 엮은 문서다. 각 단계의 수치·재현 명령은 링크된 원문서에 있다.
여기서는 **무엇을 의심했고, 무엇으로 확인했고, 무엇이 틀렸는지**를 남긴다.

## 한 줄 요약

"VLA 가 장애물을 못 피한다"는 하나의 증상 아래에 **네 개의 서로 다른 원인**이 겹쳐 있었다 —
(1) 장애물 위치를 고정한 코퍼스가 만든 **위치 쏠림**, (2) 해설(reasoning)은 장애물을 보는데 **액션 전문가에게 전달 경로가 없는
구조**, (3) 회피를 1 m 에서 잘라 먹던 **브리지 곡률 감쇠**, (4) 수집 탈락을 89% 로 만든 **노트북 CPU 절전 프로필**.
(1)·(2)·(4)는 해결했고, (3)은 원인을 확인했다. 결과: r41 은 옆 차선 장애물 앞에서 차선을 지키고(8/8), 우리 차선 장애물은
4 조건 중 3 조건에서 피한다(곡률 감쇠를 끈 설정). **회피 폭 부족은 남은 문제**이며 v1 시연 수(27)가 유력 후보다.
___

### 1. 처음 학습 방식

차가 장애물을 피하는 장면을 시뮬레이터에서 수백 번 보여주고 따라 하게 했습니다.
- 매번 장애물을 트랙의 같은 자리에 놓았습니다.
- 장애물이 없는 장면(v0)도 같은 자리에서 함께 보여줬습니다.
- 차에게 주는 명령은 두 경우 모두 "바깥 차선으로 달려"로 똑같았습니다.

### 2. 이 반복에 숨은 문제

모델 입장에서 "꺾는 장면"과 "안 꺾는 장면"의 차이는 화면 속 작은 장애물 하나뿐이었습니다. 그런데 꺾는 장면은 항상 같은 배경에서 나왔습니다.

모델은 어려운 단서(작은 장애물)를 배우는 대신 쉬운 단서를 골랐습니다.

▎ "이 배경이 보이면 대충 왼쪽으로 꺾는다."

시험 문제 답을 내용이 아니라 문제 번호로 외운 것과 비슷합니다.

### 3. 그래서 생긴 이상한 동작

- 장애물이 없어도 그 자리에 오면 슬금슬금 왼쪽으로 꺾었습니다.
- 장애물이 옆 차선에 있어도 그 자리에서는 차선을 바꿔서 거기 있는 장애물에 부딪혔습니다.
- 반대로 진짜 장애물 앞에서는 끝까지 피하지 못하고 1 m쯤 비키다 부딪혔습니다.

헷갈리게 만든 요인이 두 가지 더 있었습니다.
- 차 제어 프로그램의 설정: 저속일 때 핸들을 15% 덜 꺾게 하는 설정이 있어서, 회피를 중간에 잘라 먹고 있었습니다. 이 설정을 끄자 "피했다!"처럼 보였는데, 옆 차선 장애물로 시험해 보니 그냥 그 자리에서 무조건 꺾는 것이었습니다.
- 노트북 절전 모드: 데이터를 모을 때 CPU가 느려져서 차 위치 기록이 끊겼고, 모은 데이터의 89%가 불량으로 버려졌습니다.

### 4. 어떻게 고쳤나

	1. 장애물 위치를 매번 바꿨습니다. 트랙 전체에서 무작위로 놓으니, 배경을 외워서는 맞힐 수 없게 됐습니다.
	2. "옆 차선에 장애물이 있으면 그냥 지나가는" 장면을 다시 넣었습니다. "장애물이 보인다고 무조건 꺾는 게 아니다"를 가르치기 위해서입니다.
	3. 상황을 문장으로 알려 줬습니다. 모델 안의 "설명하는 부분"은 장애물을 제대로 보는데, "운전하는 부분"은 그 정보를 못 받는 구조였습니다. 그래서 "앞에 장애물 있음 / 길 비어 있음" 같은 짧은 문장을 운전 명령 뒤에 붙였습니다. 이 모델은 문장대로 핸들을 바꾸는 건 원래 잘합니다.
	4. 노트북을 고성능 모드로 바꿨습니다. 데이터 불량률이 89%에서 22%로 떨어졌습니다.
	5. 시험 방법도 바꿨습니다. "피했다"만 보지 않고, 옆 차선에 장애물을 둔 함정 시험도 항상 같이 봅니다.

### 5. 결과
- 해결된 것: 옆 차선에 장애물이 있으면 차선을 지키고 지나갑니다(8번 중 8번). 이전 모델은 같은 시험에서 차선을 바꿔 부딪혔습니다. 빈 길에서 괜히 꺾던 버릇도 거의 사라졌습니다.
- 반쯤 된 것: 우리 차선 장애물은 두 장소 중 한 곳에서만 끝까지 9 m까지 비키다 장애물 모서리에 걸렸습니다.
- 남은 숙제: 피하는 동작이 아직 작고 늦습니다. 이번 데이터에서  습량이 부족한 것으로 보입니다. 그래서 다음은 피하는 장면을 80개이상으로 늘리고, 5/10/20/40/80개로 나눠 학습해 몇 개면 충분한궁금해하셨던 바로 그 질문입니다.

## 출발점

- 질문: 같은 물체 회피를 몇 번 시연해야 배우나 → 스케일링 스윕(5/10/20/40/80) 계획
  ([20260929_1503](20260929_1503_avoid-data-scaling-plan.md)). 시작 조건: 학습한 박스를 폐루프에서 한 번은 피할 것.
- 현실: 램프 재학습 r36/r37 이 박스에 그대로 충돌. 시작 조건부터 막힘.

## 단계별 진행

### 1. 장애물 위치를 직선으로 옮김 (r38/r39) — 원인 아님

- 가설: 곡선 출구에서 트리거되는 위치(142)가 어렵다 → 왼쪽 직선(인덱스 70)으로 이동.
- 첫 수집은 **다른 세션의 캡처가 같은 gz 에 장애물을 남겨** 전량 폐기 → `ROS_DOMAIN_ID`/`GZ_PARTITION` 격리로 재수집.
- 결과: 반사실 반응 0.09 → 0.18 로 늘었지만 폐루프 15/15 충돌.
- 실수: 합의한 순서(박스 하나로 스윕 먼저)를 건너뛰고 7 종 다물체로 학습했다 — 박스 시연 7 개.
- 문서: [20260930_1530](20260930_1530_ramp70-relocation-result.md)

### 2. "빈 차선에서도 꺾는다" — 위치 쏠림 발견

- 확인 방법: `probe_fit` 에 장애물 없는(v0) 프레임을 넣었더니 회피 쪽으로 **+0.65 m** 예측(시연 +0.04). state 를 0 으로 해도 같음 →
  조향값 지름길이 아니라 영상.
- 확인 방법 2: 장애물이 한 번도 없던 순항 코퍼스(`probe_bg`)에서도 학습 위치 70 에서 +0.76 m, 학습 데이터가 안 지나간 곳은 베이스와 동일
  → **위치에 묶인 현상**.
- 틀린 것: 처음 제안한 "A(배경 암기)/B(구분 못 해 평균) 가르는 검사"는 두 해석이 같은 결과를 예측해 가르지 못했다. 문서에 정정.

### 3. "해설은 장애물을 본다" — 병목은 전달

- 확인 방법: `probe_narr` — r38 의 해설 헤드가 v1 10–14 m 에서 43~47% 장애물을 언급, 같은 자리 v0·순항 영상은 0~3%. state=0 동일.
- 구조 확인: `ReasoningSmolVLAPolicy` 는 해설을 prefix 위 두 번째 패스로만 계산하고 **액션 전문가는 해설 토큰을 보지 않는다.**
  v0/v1 은 명령어·state 가 같아 단서가 장애물 픽셀뿐 → 액션은 그걸 못 쓰고 위치 평균으로 빠진다.
- 이 모델이 잘하는 것은 "문장 → 조향"이다. 그래서 해설을 문장으로 액션에 넘기기로 함.

### 4. 상황 문구로 동작 조건화 (r40)

- 설계: 해설 앞머리를 고정 문구 4 종(obstacle ahead / passing / past / road clear)으로 바꿔 **동작 패스의 명령어 뒤에** 붙인다.
  해설 패스는 원래 명령어를 따로 토큰화(문구를 베껴 검출기가 붕괴하는 것 방지). 서빙은 12 토큰 해설 → 문구, 3 s 유지.
- 오프라인: 문구가 동작을 결정(빈 차선 + ahead +1.34 m, 장애물 + clear +0.34 m). r38 은 문구 무시(±0.04).
- 폐루프: 그래도 8/8 충돌. 문구가 접근 내내 ahead 인데 1 m 에서 멈춤.
- 문서: [20260930_1601](20260930_1601_situation-conditioned-action-design.md)

### 5. 1 m 에서 멈추는 이유 — 브리지 곡률 감쇠, 그리고 부정 대조

- 도구 추가: 트라이얼 궤적 기록(`avoidance_trial` TRACE, `trace_view.py`).
- 확인 방법: 브리지 파라미터만 바꾼 변형. `curv_boost_slow 0.85`(저속 지시문 곡률 85%)를 1.0 으로 → 박스 회피 성공.
- **함정**: 문구 없는 r38 도 1.0 에서 성공. 그래서 **장애물을 옆 차선에 둔 부정 대조**를 추가 → r38·r40 모두 같은 궤적으로 넘어가 충돌.
  "성공"은 위치 쏠림이 감쇠가 풀리자 끝까지 굴러간 것이었다.
- 교훈: **부정 대조 없는 회피 성공은 위치 암기와 구분되지 않는다.** 이후 모든 평가에 옆 차선 대조를 붙임.
- 문서: [20260930_1953](20260930_1953_curv-boost-and-negative-control.md)

### 6. 인식을 완벽하게 줘도 되나 — 정답 문구 오라클

- YOLO 를 붙이기 전에, 인식이 완벽하면(좌표로 만든 정답 문구) 동작이 따르는지부터 시험.
- 결과(r40): 0.85 는 옆 차선 유지 O / 우리 차선 충돌, 1.0 은 우리 차선 회피 O / **clear 에도 옆 차선 충돌**.
  문구는 쏠림을 줄이지만 막지 못함 → 브리지 파라미터 문제가 아니라 **동작 모델의 위치 쏠림을 없애야** 함.
- 중간에 랩서버 1 시간 단절(네트워크) — 재개 명령을 문서에 남기고 복구 후 이어 실행.
- 문서: [20260930_2107](20260930_2107_oracle-situation-stage1-partial.md)

### 7. 위치 무작위 + 옆 차선(v2) 코퍼스 (r41)

- 설계: 장애물 위치를 에피소드마다 트랙 전체에서 무작위, v2(옆 차선 장애물, 차선 유지, 문구 clear)를 다시 넣음.
- 막힘: 시범 수집 탈락 89%. 원인 추적 —
  - 탈락 사유 두 개(tf 끊김, 곡선 보간 오차)가 모두 **위치 스트림 공백**.
  - 낮 수집(74% 통과)과 같은 코드인데 스트림 속도가 느림 → CPU 확인 → governor `powersave`/`balanced`, 평균 2 GHz.
  - **`performance` 로 바꾸자 같은 시드 2/9 → 7/9.** 레코더의 "늦게 온 메시지 = ego 바뀜" 오판도 속도 × 경과 시간 허용치로 수정.
- 결과(r41, 정답 문구):

  | | 0.85 | 1.0 |
  |---|---|---|
  | 우리 차선, 인덱스 70 | 충돌 | 충돌(1.9 m 에서 모서리) |
  | **옆 차선, 인덱스 70** | **유지** | **유지** |
  | 우리 차선, 인덱스 142 | 충돌 | **회피** |
  | **옆 차선, 인덱스 142** | **유지** | **유지** |

  빈 차선 쏠림: r38 +0.65 → r40 +0.33 → r41 +0.25 m(위치 특이적 정점 소멸).
- 문서: [20260930_2302](20260930_2302_div-corpus-pose-stream-and-clips.md)

## 무엇이 해결됐고 무엇이 남았나

| 원인 | 상태 | 해결/확인 수단 |
|---|---|---|
| 위치 쏠림(고정 위치 코퍼스) | **해결** — 옆 차선 대조 8/8 유지 | 위치 무작위 + v2 코퍼스 |
| 해설→동작 전달 경로 없음 | **우회** — 고정 상황 문구를 명령어로 | `--situation-prompt` / `--situation-from-reasoning` |
| 브리지 곡률 감쇠(0.85) | **원인 확인**, 기본값은 유지 | 변형 실험 + 궤적 기록. 1.0 전환은 순항 회귀 확인 후 |
| 수집 탈락(CPU 절전) | **해결** | 수집 전 `powerprofilesctl set performance` |
| 회피 폭 부족(인덱스 70 0/2) | **남음** | 유력: v1 27 개뿐 → v1 추가 후 스케일링 스윕 |
| 해설 검출기 약화(r41 10–14 m 4/30), 사람 미검출, 차선 구분 못 함 | 남음 | 실차 경로는 YOLO 로 문구 공급 계획 |

서술 주의(범위): r41 이 하는 일은 **"상황 문구에 따라 차선을 바꾸거나 유지"**다. 장애물을 "이해"한다고 쓰지 않는다 —
정답 문구 오라클로 측정했고, 모델 자신의 해설 검출은 약하다.

## 방법론 교훈

1. **증상 하나에 원인이 여럿일 수 있다.** 한 원인을 고칠 때마다 다음 원인이 드러났다(위치 → 전달 → 감쇠 → 위치).
2. **부정 대조를 먼저.** "피했다"는 옆 차선·빈 차선에서 차선을 지킬 때만 의미가 있다.
3. **인식과 동작을 분리해 측정.** 정답 문구 오라클로 동작만 떼어 보니 "브리지를 바꾸면 된다"는 착시를 피할 수 있었다.
4. **궤적을 남겨라.** 최근접 오프셋 하나로는 "멈춤"과 "갔다가 복귀"를 구분 못 한다.
5. **환경 변수부터 의심.** 같은 코드의 탈락률이 74% → 11% 로 바뀌면 코드보다 환경(공유 gz, 전원 프로필, 서버 네트워크)을 본다.
   이번에 세 번(다른 세션의 gz 공유, 랩서버 단절, CPU 절전) 그랬다.
6. **틀린 건 지우지 말고 정정.** A/B 검사 설계 오류, 순서 위반(7 종 먼저 학습)을 각 문서에 남겼다.
