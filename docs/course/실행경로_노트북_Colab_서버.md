## 원인: 평가 도구의 물체 생성 버그 (22:25 판의 "첫눈 53 %" 는 틀림)

**"못 찾음" 은 VLM 이 아니라 화면에 물체가 없어서였다.** 순서대로 확인한 것:

1. 오라클 첫 프레임 30 장 비교에서 서버 · Colab 답이 같았다 (둘 다 16/30). 그런데 그 0 번 프레임은 물체 생성보다 녹화가 먼저 시작돼 **목표가 아직 없는 프레임**이 섞여 있었다 (3 번 프레임부터 보임). 5 번 프레임으로 다시 재면 **27/30**.
2. 노트북 GPU 경합(정책 + 시뮬 렌더링)을 의심해 같은 장면 카메라를 찍었다: 정책 있을 때 · 없을 때 모두 15 Hz, 영상 같음 → 원인 아님.
3. 서버 VLM 에 3 s 지연(`tools/slow_proxy.py`)을 넣어 Colab 흉내 → 17/20. 지연만으로는 13/20 이 안 나온다.
4. 실패 장면만 따로 다시 돌리면 3/3 첫 요청에 찾는다 → 같은 장면이 실행마다 다르게 실패.
5. goal_node 가 VLM 에 보낸 영상을 저장(`debug_dir`)해 보니 "없음" 시행의 영상에 **물체가 하나도 없었고**, 그 순간 시뮬에 `pt_obj0` 이 없었다.
6. 원인(정황): 평가가 같은 이름으로 지웠다 다시 만들며, 지우기가 늦게 반영되면 새로 만들기가 실패하고 확인은 '이름 있음' 으로 통과 → 곧 옛 물체가 지워진다.
   수집 GUI 는 매번 새 이름이라 이 문제가 없었다.
7. 고침: 시행마다 새 이름 + 놓은 뒤 모델 목록 확인 → 같은 느린 VLM 조건 **19/20 · 접촉 0** (p2F).

남은 실패 1 건(P14)은 진짜 인식 문제다: 영상에 물체가 있었고, VLM 은 `go_dog`(봉제 강아지)을 **"teddy bear"** 라 부른다.

### 학생 한 명이 VLM 을 얼마나 부르나
- 평가 P 20 회에서 VLM 호출 26 번 (p2N · p2C 10-16 debug 영상 수) → **시행당 약 1.3 번**. 물체를 찾은 뒤에는 라이다로 따라가며 VLM 을 다시 부르지 않는다.
- 시행 하나가 놓기 포함 약 25 s → 쉬지 않고 시행을 반복하는 학생 한 명 ≈ 초당 0.05 건.
- 50 명이 쉬지 않고 반복해도 ≈ 초당 2.6 건 — 처리량(2~4 건/s) 언저리. 응답이 몇 초 늦어질 수 있으나, Colab 경로(중앙값 4.5 s)로도 19/20 이었다.
- **위험한 경우:** 50 명이 한꺼번에 보낼 때 (예: "자, 다 같이 보내 보세요"). 처리량으로 계산하면 마지막 학생은 15~20 s 기다린다 — 추정, 50 동시는 안 재 봄. 팀별로 순서를 돌리면 피한다.
- 실차 8 팀이면 동시 8 건 이하 → 응답 1~4 s, 문제없음.

### 서버 VLM 을 강좌에 쓰려면 남은 일 (아직 안 함)
1. **외부 접속 (필수):** 서버 ollama 는 서버 안(127.0.0.1)에서만 받는다. 온라인 수업 때 집에 있는 학생이 붙으려면 터널 · 공개 주소가 필요하다.
   ollama 에는 인증이 없어 주소가 퍼지면 누구나 연구실 GPU 를 쓴다 → 앞에 **접속 토큰을 확인하는 프록시**를 둔다 (`ros2_vla/tools/slow_proxy.py` 를 고쳐 만들 수 있음).
2. **서버 하나가 멈추면 50 명이 다 멈춘다:** Colab VLM 노트북(`colab/vlm_server.ipynb`)을 예비로 남긴다.
3. **강좌 기간 GPU 확보:** 연구실 다른 작업과 3090 이 겹치지 않게 미리 비우거나 예약한다.
4. **학생 노트북이 더 큰 위험일 수 있다:** 시뮬을 개인별로 하면 50 명 모두 자기 노트북에서 시뮬 + 정책을 돌린다 (이 노트북 RTX 4060 기준 GPU 1.8 GB · RAM 약 4.5 GB).
   GPU 없는 노트북 · RAM 8 GB 노트북은 아직 안 재 봄.
5. 50 명이 실제 시행 간격으로 요청하는 부하 시험(클라이언트 50 개)은 사전 등록 뒤에 한다.

- 지금 모델(p2)은 물체로 가기만 배웠다. 차선 주행 문장에는 반응하지 않는다 (학습 데이터 = 물체 이동 98 에피소드).

### GUI 정리 · Qwen 대화 (10-16 오후)
- 뺀 것: 문장 묶음 · 표현 고르기, 시험 기록 칸(판정은 `tools/eval_minimal.py` 가 함), 주행 모드 버튼(수동 · VLA · 비상 정지).
  남은 조작: 채팅 = VLA 주행, 전방 카메라 클릭 = 수동, Esc 또는 "정지" = 정지.
- 라이다 그림(전방 카메라 옆)은 앞쪽 반만 그린다 (수집 GUI 도 같음).
- 넣은 것: **05 Reasoning** 칸 — sant-vla 와 같은 꼴(탭 "모델 reasoning" · "장면 해설" · "주행 기록" + 상태 줄). 장면 해설 = 채팅에서 화면을 물었을 때 Qwen 답, 주행 기록 = 입력 · 답 · 주행 시작/정지. 문장을 어떻게 나눴는지, 목표 노드가 보고한 것(박스 → 방위 · 라이다 거리, 다시 보는 중, 도착),
  정책에 들어가는 문장을 시각과 함께 보여 준다. sant-vla 의 "모델 reasoning" 과 달리 **정책(SmolVLA)이 낸 추론이 아니다** — p2 정책은 추론 문장을 내지 않는다.
- 대화: 고정 답 대신 목표 노드와 같은 Qwen2.5-VL 이 답한다 (`course_vla/chat_assistant.py`).
  - 문장 나누기 순서: "정지" → 바로 멈춤 / "○○로 가" 꼴 → 바로 목표 노드 (p2N 경로) / 차선 · 속도 · 학습 문장 → 정책 /
    나머지 → Qwen 이 **글만 보고** 의도(goto · chat)를 가름 → goto 면 그 문장을 목표 노드에, chat 이면 전방 영상 + 차 상태를 보고 답.
  - 의도와 답을 영상과 함께 한 번에 물으면 "안 보인다"는 판단이 의도를 덮었다("소화전 있는 데까지 데려다줘" → 대화, "상자 앞에 세워줘" → 대화). 그래서 나눴다.
  - 의도 판단 시험 24 문장(서버 7B): 22/24. 틀린 2개("…쪽으로 가볼까?", "…까지 가 줄 수 있어?")는 GUI 에서 "○○로 가" 규칙이 먼저 잡는다.
    한 번 잰 것이고 사전 등록 측정은 아니다.
  - 사건(찾음 · 도착 · 못 찾음 · 지나침)도 Qwen 이 사실만 받아 말로 바꾼다. 연결이 안 되면 고정 문장.
  - 한계(학생 안내): 날씨처럼 모르는 것을 지어낼 때가 있다("내일 날씨 맑음"). 강의 일정은 모른다고 답하게 고쳤다. 대화로는 차가 움직이지 않는다.
  - 부하: 대화 한 번 = Qwen 호출 2번(의도는 글만이라 0.1 s, 답은 영상 포함 0.7 s), 물체로 가기 한 번에 말 바꾸기 호출이 2~3번 더 든다(글만, 0.3 s).
    50명이 서버 VLM 을 같이 쓰면 위 부하 추정보다 늘어난다 — 재지 않음.
- 실행: `drive.launch.py` 가 `ollama_host` · `vlm_model` 을 GUI 에도 넘긴다 (`--vlm-host`, `--vlm-model`).

## 물체 텍스처가 서로 섞이던 문제 (10-16 13시)
- 증상: 로봇(안드로이드) 모델이 Gazebo 창에서는 초록색인데, 차량 전방 카메라(= 모델 입력)에서는 얼룩무늬로 보였다.
- 원인: `go_dog` · `go_horse` · `go_dino_5` · `go_triceratops`(로봇) 4개가 텍스처 파일 이름(`texture.png`)과 재질 이름(`material_0`)이 같다.
  시뮬 서버의 카메라 렌더러가 같은 이름이면 먼저 불러온 텍스처를 다시 쓴다 → 먼저 놓인 모델의 무늬가 다른 모델에 입혀진다.
  Gazebo 창(따로 렌더링)은 불러온 순서가 달라 멀쩡해 보였다.
- 영향: p2N 평가 영상(`data/log/p2N_debug/`)에서 **말이 강아지 무늬**였다. 그 시뮬 세션에서 무엇을 먼저 놓았느냐에 따라
  말 · 공룡 · 로봇 · 강아지 중 셋이 다른 무늬였을 수 있다 → 지금까지의 수집 데이터(p2 학습)와 평가 영상에도 들어 있을 수 있다. 몇 장인지는 세지 않았다.
  목표 도착 판정(P 19/20 · 20/20)은 VLM 이 모양으로 물체를 찾았으므로 유지되지만, "카메라에 보인 장면"은 의도와 달랐다.
- 고침(ros2_vla): 4개 모델의 텍스처 · 재질 이름을 모델별로 바꿈 (`go_horse_texture.png`, `go_horse_material` …), `colcon build --packages-select course_sim`.
  확인: 켜 둔 시뮬에 새 경로로 복사한 로봇 · 강아지를 놓고 전방 카메라를 저장 → 로봇 초록색, 강아지 제 무늬.
- **시뮬을 한 번 다시 켜야 반영된다.** 이미 떠 있는 시뮬은 옛 메시를 기억해 로봇이 텍스처 없이 흰색으로 나온다.
- sant-vla(`src/simulation_pkg/models`)에도 같은 이름을 쓰는 모델이 7개 있다(go_dino_trex · go_dino_3 · go_horse · go_teddy · go_dog · go_triceratops · go_dino_5).
  연구 데이터(g5d 등)와 얽혀 있어 고치지 않았다.

### 3D 화면 라이다 영역 · 03 칸 (10-16 13시)
- 라이다 하늘색 영역이 트랙 위에서 안 보이던 원인: 트랙 바닥 텍스처(`race_track/.../track.png`)가 RGBA 라서 바닥이 반투명 물체로 그려졌고,
  보는 각도에 따라 바닥이 반투명 부채꼴 위에 덮였다(트랙 밖 회색 바탕 위에서만 보임). 알파는 전부 255 라 RGB 로 바꿈 → 색은 같음(픽셀 비교 일치).
  다시 켠 뒤 전체 탑뷰에서 트랙 위 부채꼴이 보이는 것 확인. 차량 추적 시점은 확인하지 않았다.
- 라이다 영역은 GUI 를 켜면 3초 뒤 자동으로 켜진다 ("라이다 영역" 버튼으로 끌 수 있음). 그리는 방식: 처음엔 마커 자세를 차 자세로 매번 다시 보냈는데 10 Hz 는 끊겨 보였고 30 Hz 는 화면 전체가 끊겼다(GUI 프로세스 CPU 40 %). 지금은 마커를 차 모델에 붙이고(`parent: ego_vehicle`) 모양만 새 스캔마다(10 Hz, 광선 절반) 보낸다 → 따라가기는 Gazebo 가 그릴 때마다 하고, Gazebo 화면 CPU 14 → 16 %, GUI 프로세스 약 5 %.
- 03 칸: 전방 카메라 칸 너비를 영상 비율(4:3)에 맞추고 남는 가로를 라이다 그림에 줌. 라이다 그림 정면의 좁은 부채꼴 선 = 전방 ±15° 구간(`FRONT_HALF_ANGLE_DEG`),
  이 구간의 가장 가까운 점이 "전방 거리"이고 안전 정지(점선 원) 판정에 쓰인다.

## 한 줄로 켜고 끄기 (10-16, `ros2vla`)
- `~/.bashrc` 의 `ros2vla` (환경만), `ros2vla up` · `ros2vla down` · `ros2vla status` → `ros2_vla/scripts/ros2vla.sh`.
- `up`: 서버 VLM 터널(없으면 ssh 로 엶) → 시뮬(떠 있으면 재사용) → 정책 서버(p2, 1~2분) → 주행 노드 + 테스트 GUI. 옵션 `--model`, `--vlm <Colab 주소>`.
- 끄기: GUI 창 닫기 또는 Ctrl+C → 시뮬까지 전부 끈다 (`drive.launch` 의 GUI 노드 `on_exit=Shutdown`). 따로 `ros2vla down`.
- GUI 는 켤 때와 닫을 때 장면을 비우고 차를 2차선 출발선으로 옮긴다. 닫을 때 정리는 따로 띄운 프로세스가 한다
  (창 안에서 하면 '응답하지 않음' 이 떴고, stop.sh 가 강제 종료하면 끊겼다).
- 10-16 13:5x 사용자 실행에서 GUI 가 "응답하지 않음" · Gazebo 화면이 안 붙고 따로 뜸 · 전체화면 안 됨: 라이다 영역을 GUI 프로세스 안 스레드로 그렸는데 `gz.transport` 의 request() 가 응답을 기다리는 동안 GIL 을 놓지 않아, Gazebo 화면이 붙기 전(응답 없음 0.5 s 씩) 메인 스레드가 멈췄다 (faulthandler 스택: 메인 = paintEvent 에서 GIL 대기, 마커 스레드 = request). 라이다 영역을 별도 프로세스(`python -m course_vla.lidar_marker`)로 옮김. 다시 시험: 메인 스레드 정상(poll), Gazebo 화면 붙음, 최대화 됨, 창 닫기 → 7 s 뒤 전부 꺼짐, Traceback 0. GUI 가 멈추면 `kill -USR1 <drive_studio pid>` 로 모든 스레드 스택이 터미널에 찍힌다.
- 시험(10-16 13:4x): up → 모두 1개씩 뜸, 시작 정리 완료 → 물체 1개 놓고 창 닫기 → 종료 정리 1개 · 출발선 완료 → 9초 뒤 프로세스 0.

## 강의 준비 체크리스트

학생 한 팀이 연구실 서버 없이 "말로 물체 지정 → 가서 서기" 를 돌리는 순서다. 오늘 실제로 겪은 함정을 각 단계에 적었다.

**노트북 준비**

- [ ] ChatGPT · Chrome · Whale 등 브라우저와 큰 앱을 닫는다 — 닫기 전 가용 2 GB, 닫은 뒤 9.8 GB
- [ ] `free -g` 로 가용 RAM 6 GB 이상 · 스왑 여유 확인
- [ ] 시뮬은 한 개만 (`scripts/sim.sh status`). 다른 터미널 · 다른 세션이 같은 시뮬에 평가를 돌리지 않게 (10-15 두 평가가 겹쳐 시행 6 개 무효)
- [ ] 모델: Colab 에서 받은 `pretrained_model` 을 `data/models/<팀>/` 에 푼다

**팀 Colab 에서 VLM 띄우기** (`ros2_vla/colab/vlm_server.ipynb`, 약 5 분)

1. Colab → 파일 → 노트 업로드 → 런타임 유형 **T4 GPU**
2. 셀 1~5 차례로. 2번 셀은 `zstd` 를 먼저 설치해야 한다 (없으면 ollama 설치가 조용히 실패 → `FileNotFoundError: 'ollama'`) — 고침 반영됨
3. 3번 셀 qwen2.5vl:7b 받기 6 GB, 2~3 분
4. 5번 셀의 `https://…trycloudflare.com` 주소를 노트북에 입력. **첫 VLM 답은 28.7 s** (데우기) — 두 번째부터 약 4 s
5. 평가 · 시연 동안 Colab 탭을 열어 둔다 (유휴 90 분 · 최대 12 시간이면 끊기고, 다시 띄우면 주소가 바뀐다)

**노트북에서 실행**

```
scripts/sim.sh up
scripts/drive.sh --model data/models/<팀>/pretrained_model ollama_host:=https://…trycloudflare.com
```

- 채팅에 `Go to the red cone.` 또는 `빨간 꼬깔로 가줘` → [▶ VLA 주행]. 물체는 6~10 m, 화면 좌우 ±25° 안에
- 끄기: `scripts/stop.sh` (GUI · 정책 서버), `scripts/sim.sh down`

**주의**

- trycloudflare 주소는 아는 사람 누구나 그 VLM 을 쓸 수 있다. 팀 밖에 공유 금지
- 학습(train_smolvla.ipynb)과 같은 Colab 세션이면 GPU 를 나눠 쓴다 — 학습이 끝난 뒤 띄운다
- VLM 이 물체를 못 찾으면 차는 서 있다(안전한 실패). 엉뚱한 박스를 치면 다른 물체 쪽으로 간다 — 시연 배치는 물체 간격을 둔다
- 노트북 ollama 로 VLM 을 돌리지 말 것 (3B 도 CPU 로 내려가 RAM 10 GB · 82 s)
- 물체 이름은 VLM 이 보는 이름에 맞춘다: `go_dog` 은 "teddy bear" 로 본다 → 학생에게 "곰 인형 · 강아지 인형" 으로 부르게 하거나 다른 물체로
- Colab 노트북의 ollama 0.33.1 고정은 10-16 실행에서 적용되지 않았다(0.40.5 로 설치됨). 그래도 19/20 이라 버전 고정은 필수가 아니다
- 첫 VLM 요청은 30 s 가까이 걸린다(모델을 GPU 에 올림). 3번 셀의 예열("hi")이 돌았는지 확인하거나, 평가 · 시연 전에 한 번 물어 둔다
